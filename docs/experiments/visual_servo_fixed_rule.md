## 1. 规则

ArUco码中心落在画面的左/右/上/下区域时，相机向该方向移动1cm；落在中间区域时向前
移动1cm；到达停靠条件后保持。

| 项 | 取值 | 来源 |
|---|---|---|
| 中间区域 | 每轴归一化0.3–0.7（640×480下即横192–448、纵144–336像素） | 规则，`--rule-band 0.4` |
| 单步 | 10mm | 规则，`--rule-step-mm 10` |
| 停靠判据 | 标记边长≥120px | 像素判据，不依赖标定 |
| 次判据 | 名义深度≤100mm | 依赖内参，正常姿态下先被边长判据满足 |
| 前向门限 | 中心误差≤24px才允许前进 | 避免带着偏置前进 |

区域判定取归一化偏差最大的轴，因此斜向偏差只产生一次单轴动作。

## 2. 为什么"往前1cm"以前做不好

第一轮收尾已经确认回中可用（10次纠偏、27步、最终中心距离中位39.4px），但完全没有
前向能力。原因不是参数没调好，而是三件结构性的事：

**（a）第一轮的2×2响应矩阵没有深度列。** 该矩阵的两列是底座与手腕俯仰的
像素/计数响应，没有任何一列会改变标记的表观尺寸，因此"前进"在当时根本没有可执行方向。
换参数、缩死区都无法从这张表里读出深度。

**（b）单纯抬升会把深度信号淹没在姿态变化里。** 在记录姿态下，相机前向1cm约等于
`shoulder_lift +16`、`wrist_flex −15`计数。若只抬升4°（约14计数），标记在图像里纵向
移动 **66.3px**，而1cm前向带来的边长变化只有 **1.68px**——相差39倍，而且看起来正是
一个"居中误差"，会被回中逻辑当作偏差纠正掉。

**（c）横向1cm落在死区内。** 300mm处横向1cm约25.9px，在记录姿态下只需
`shoulder_pan` **5计数**。第一轮证据显示该臂小于5计数不动，且阈值随方向/姿态变化，
所以小请求必须升到最小可执行幅度。

还有一条量化约束：1计数`shoulder_lift`约4.90px、1计数`wrist_flex`约5.68px，
即前后摆动的抵消精度有约 **5px** 的整数编码器底噪，已经是1.68px深度信号的3倍。
所以前向步不可能"零漂移"，闭环必须允许它在相邻步之间做少量居中修正。

## 3. 本轮做法

决策、数值、执行三层分开，决策与数值都不持有相机或串口：

| 层 | 文件 | 职责 |
|---|---|---|
| 数值 | `control/visual_servo/camera_step.py` | 把1cm相机平移转成一阶图像效应，再解成量化关节目标；死区主动集、整步等比缩放、多尺度回退、响应模型 |
| 决策 | `control/visual_servo/fixed_rule.py` | 五区域分类、相位（align/approach）、预算与停靠判定、实测反馈折叠 |
| 执行 | `applications/visual_servo/fixed_rule_servo.py` | 唯一设备所有者：取帧、读编码器、下发目标、读回、记录 |
| 守卫 | `applications/visual_servo/joint_center.py` | `BoundedJointMotion`，与回中循环共用同一套安全判定 |

关键设计点：

- **以图像效应为目标，不以相机位姿为目标。** 1cm横向在这条臂上无法表达成真正的平移
  （5计数底座主要是偏航），但标记确实移动了预期的像素数，这才是规则真正需要的量。
- **前向必须是"抬升+手腕反向"的配对，并用整步等比缩放。** 若只钳位其中一个关节，
  另一个关节会保留，姿态平衡被破坏，前向步就变成大漂移。因此超限时按同一比例缩短
  整步，并如实报告 `achieved_fraction`。
- **横向/纵向用单关节。** 一个关节的像素/计数响应要么动到预期像素数、要么没动，
  可归因；最小范数解会混三个关节，失败时无法判断是谁的问题。候选关节里**优先已表征的
  轴**：一旦引入偏移，"没有先验"的轴会显得最便宜，选它就等于用一次超时去学它的阈值。
- **死区主动集。** 预测实际幅度落在 `min_effective_counts` 以内、或请求本身跨不过该轴计数
  偏移的关节，被移出任务集再重解，预测描述"臂会做什么"而不是"请求了什么"。
- **响应模型是"偏移 + 增益"，不是比例。** 按关节+方向各存一份偏移和一份增益
  （`moved = max(0, |request| − offset) × gain`），只由实测更新，增益clip到[0.45,1.25]。
  比例模型无法表达"请求了却一动不动"，详见第7节。
- **关节单步上限与守卫必须逐位一致。** 缩放后`rint`会把13.6计数圆成14，也就是4.12°，
  刚好越过4°上限；守卫于是拒绝一个"规划器声称合法"的步，闭环就在边界上永久停住。
  现在超出上限时向零截断，并在notes里留`truncated_to_joint_limit`。
- **被上限截断的步要执行，不能拒绝。** 关节上限生效时，这一步已经是该方向允许的
  最大动作；若因为"只达成目标的30%"而拒绝，闭环会在该距离永久停住。现在这种情况
  标注`cap_limited_to_x`后照常执行，由到位、漂移、卡死守卫继续把关。
- **漂移只统计计划之外的部分。** 一个纵向1cm修正本来就会让标记移动约28px，拿原始
  位移和25px限值比较会把每次正确修正都标成故障；改为比较"实测位移−预测位移"。

负方向要先吃掉约7个计数，所以16计数的请求只剩约9.5个计数的真实位移，而旧口径把16个计数
全算成位移。也就是说，第7节那次修改在不碰任何参数的情况下，让"1cm"实际变成了0.76cm；
5°上限看起来没动，效果却变差了。

因此2026-10-18的放宽同时抬了两个数，而且缺一不可：

- `max_joint_step_deg` 5 → **12**：记录姿态下做完整1cm需要约 `+21/−22` 计数、`+5.15/−4.80` 度，
  12°不再截断它。
- `rule_max_request_counts` 18 → **40**：22计数本身就超过旧的18计数上限，只抬角度上限
  仍然会被计数上限截回去。两个上限必须一起抬，否则抬了一个等于没抬。

### 4.1 预算放宽后的实测边界（2026-10-18）

放宽是操作者在现场确认的**许可**，不是量出来的工作空间。为了不让"许可"变成"猜测"，
把闭环在同一个缺陷模型下用新预算重放了一遍，得到三条不该再靠估的结论：

| 起始距离 | 结束 | 深度 | 边长 | 累计行程 | 关节偏移 |
|---|---|---|---|---|---|
| 300mm | 到停靠 | 300.0 → 167.5mm | 126.3px | 132.2mm | 69.7° |
| 340mm | 到停靠 | 340 → 175.9mm | 120.0px | 164.4mm | 86.5° |
| 380mm | 到停靠 | 380 → 174.6mm | 121.0px | 205.1mm | 107.1° |
| 400mm | 到停靠 | 400 → 173.4mm | 121.9px | 226.4mm | 119.4° |
| 420mm | **偏移预算停止** | 420 → 184.6mm | 114.4px | 235.5mm | 125.6° |
| 440mm | **偏移预算停止** | 440 → 208.9mm | 101.1px | 231.2mm | 122.9° |

> 勘误：本表此前的 420mm 行误抄了 440mm 那一行的数字（209mm / 101.1px）。
> 用当前代码树（计数偏移模型已接入闭环）重测后，420mm 实际停在 184.6mm——差 9mm 到停靠，
> 仍然是没到，但差距比原先记录的小得多。300–400mm 四行重测后逐列不变。

**（a）120°不是随手取的倍率，它就是400mm起步的代价。** 300mm只要69.7°，每多100mm
起始距离多耗约50°。所以"能否到停靠"的判据不是"预算够不够大"，而是"起始距离在不在
400mm以内"；现场更稳妥的做法是**从380mm以内起步**，留20°余量。

420mm 正好卡在边界上，而且它对预算不是单调的：120° 与 125° 都停在 184.6mm，
**130° 才到停靠（175.7mm、32步）**。所以"把预算再抬10°"对 420mm 有效、对 440mm 反而
更差（见(c)）——这不构成"抬预算就能更远"的普遍结论，仍然是起点距离在说话。
要不要为 420mm 抬到 130° 是操作者对净空的确认，不是本文单方面改的默认值。

**（b）真正会耗尽的是 `shoulder_lift`，不是 `wrist_flex`。** 以440mm起步、120°上限那一次为例
（就是下面(c)的对照组）：`shoulder_lift` 从 −44.7° 走到 +78.2°，一个人吃掉了全部122.9°偏移，
自己离URDF上限 +100° 只剩21.8°；而 `wrist_flex` 只走了53.5°，还剩61.3°没用。
这一点此前在配置注释里写反了（写成"wrist_flex 会先碰到自己的95°行程"），现在按实测更正。
表中420mm那一行是同一个模式，125.6°几乎全部来自 `shoulder_lift`。

**但要说清 +100° 是哪一端。** 它是 `shoulder_lift` 的**机械行程端**，不是"向前伸的极限"：
固定其余关节、只动这一条轴时，相机到标记的距离先减后增，**最近只到 330.6mm（在 +13°）**；
再往上就翻过去了，到 +100° 时相机已经在标记平面**之后**（名义深度 −528.6mm，
|cam→marker| 530mm）。所以：

- 这条轴**单独**永远到不了 120px 停靠（它自己的最好成绩是 330.6mm），前向能力本来就来自
  `shoulder_lift`+`wrist_flex` 的配对，不是单轴。
- 440mm 那一次停在 209mm，是因为**这一条轴的机械行程用完了**（+97.35°，上限留 2° 余量），
  不是相机已经无法更近——在终点姿态上再增加 lift 的边际值仍是 −2.64mm/度。
  换句话说：**不是"前向几何极限"，是"这条轴被推到自己的行程尽头"**。这两件事必须分开说，
  否则会得出"再抬预算也没用"的错误结论（4.2 的实测正是为了排除这一点）。

**（c）440mm起步在任何预算下都到不了停靠。** 把上限单独抬到135°只到190mm；抬到145°
或160°反而更差——闭环在34步、188.6mm处停下并报
`没有可执行步（no executable step）：… 所有关节都落在死区内`。两个原因叠在一起：
多出来的角度没有变成接近距离，而是被额外的对齐步吃掉了（对齐5步→8步，`shoulder_lift`
照样往上走）；等到 `shoulder_lift = 97.35°`，距自己的**机械上限**（+100°，留2°余量）只剩
2.65°，任何候选轴的整步都跨不过计数死区，规划器连一个合法步都给不出。
注意这里卡住的是**这条轴的行程**，不是"相机已经无法更近"（见上一条）：
`shoulder_lift` 是被前向原语一路推到尽头的那条轴，而 `elbow_flex` 还有82°没用。
至于把这个负荷分给 `elbow_flex` 能不能解决问题，4.2 给了实测答案：不能。

### 4.2 为什么不让 elbow_flex 分担前向位移（已实测否决）

`elbow_flex` 在440mm全程还剩约82°没用到，而它的前向效率并不低：
**0.723 px/度**，`shoulder_lift` 是 **0.714 px/度**，两者几乎等价。所以"把负荷分给这条闲置轴"
看上去是显然的改进，本节记录它为什么不是。

**先看等价家族。** 在记录姿态、300mm、目标为纯前移1cm（`[du,dv,dsize]=[0,0,2.35]`px）时，
固定 `elbow_flex` 的计数，解出满足同样图像目标的 `shoulder_lift` / `wrist_flex` 计数：

| elbow_flex 计数 | shoulder_lift | wrist_flex | 单步最大负载 \|计数\| |
|---|---|---|---|
| 0 | 17.5 | −15.1 | **17.5** |
| 6 | 11.8 | −18.1 | 18.1 |
| 12 | 6.1 | −21.1 | 21.1 |
| 18 | 0.4 | −24.1 | 24.1 |

每 6 个 `elbow_flex` 计数能换掉约 5.7 个 `shoulder_lift` 计数，但要**多付约3个 `wrist_flex` 计数**。
原因是 `elbow_flex` 的竖向移动是 `shoulder_lift` 的 **1.53 倍/计数**，这份额外竖向位移全得由腕轴
反向抹平。而腕轴已经是这对关节里出力更大的一个，于是"单步最大负载"单调上升——也就是说
分担让这一步**更贵**，不是更便宜。这正是最小范数解把 `elbow_flex` 留在死区里的原因，
不是它没想到。

**再看闭环。** 给 `shoulder_lift` 一个代价（1.0/1.5/2.0/2.5），并可选地按各轴**剩余偏移预算**
再偏置，四种起点各跑一遍（预算120°/12°/40计数，60步上限）：

| 方案 | 300mm | 380mm | 400mm | 440mm |
|---|---|---|---|---|
| 统一代价（现在） | 到达·16步 | 到达·25步 | **到达·29步** | 预算停·209mm |
| 代价1.5 | 到达·24步 | 到达·33步 | 到达·37步 | 预算停·206mm |
| 代价1.5+预算偏置 | 到达·23步 | 到达·28步 | 未到达·119.6px | 步数耗尽·218mm |
| 代价2.0+预算偏置 | 到达·32步 | 预算停·119px | 步数耗尽 | 步数耗尽·229mm |
| 代价2.5 | 到达·32步 | 到达·32步 | 到达·36步 | 预算停·222mm |

**没有任何一档优于统一代价**：唯一的400mm到达且步数最少的是统一代价。

**最后一个原因在撞墙之后才显现。** 440mm 时 `shoulder_lift` 一旦到限，`elbow_flex`+`wrist_flex`
这一对会**逐步反向震荡**：请求在 `(−24, +38)` 与 `(+26, −38)` 之间来回，达成率 0.12–0.32，
边长几乎不动。所以那之后的差距不是"负荷分配没调好"，而是这个姿态已经没有可用的前向步。

结论：分担前向位移不能延长可达距离。真正有效的仍然只有两条——**起点放在380mm以内**，
或者换一条不同的接近几何（例如底座参与），后者不在本次范围。

回归断言见 `tests/test_fixed_rule_servo.py::ElbowShareTest`：它钉住"每多用一点
`elbow_flex` 就要多付一点 `wrist_flex`"这条单调关系，避免以后又从效率表里读出"这条轴在闲置"。

原始口径（未放宽前）保留在这里以便对照：从250mm起步、用40°累计关节预算时，规则在
边长118.9px（名义深度178mm）处因**关节偏移预算**停止，距停靠还差约2mm。这是正常结束，
不是失败；日志的`hold`事件会写明是哪一条预算。

## 5. 标定口径

深度只影响两件事：名义停靠距离和交互矩阵的量级。停靠用像素判据，所以**不依赖内参**；
但交互矩阵按1/深度缩放，焦距错了会直接改变每步的关节幅度。

本轮改为从 `calibration/vision/camera_intrinsics.json` 读取实测内参
（`fx=844.45`，`cx/cy=(346.0, 210.6)`），不再使用早期实现里的占位值554。若继续用554，
深度会被低估1.52倍，求解器会以为标记更近，同样像素目标下给出约1.52倍的关节幅度。

需要保留的保留意见：

- 内参文件的平均重投影0.355px、RMS 0.408px，但畸变系数（k2≈2.09、k4≈−11.3）与41.6°
  水平视场并不自洽，该标定本身的可信度未独立复核。
- 手眼平移约 `(21.47, 17.79, −61.43)mm`，但同一文件记录的标定板原点在base系
  `(865, 93, 26)mm`、z方向RMSE 38.6mm，与桌面作业距离不符。矩阵合法不等于物理精度。
- 因此启动时会打印"名义深度"，并要求操作者用实际距离核对；不一致时应当停止，而不是
  相信这个数字。
- 不做去畸变：主点附近0.1%以内，而规则的对齐相位本身就把标记约束在中央区域。

## 6. 守卫与停止条件

与回中循环共用 `BoundedJointMotion`，因此以下判定在两个入口完全一致：

| 类别 | 条件 |
|---|---|
| 下发前 | 标定范围、URDF限位+2°余量、累计关节偏移、单步上限、行程预算 |
| 下发前 | 必须在写目标前重新取帧并重新检测到目标；扭矩/状态逐轴读回；目标读回校验 |
| 执行中 | 1秒到位租约；稳定200ms；到位与"稳定的部分响应"分开记录 |
| 执行中 | 丢目标或断帧 → 写入实测位置作为保持目标后抛出，不继续发动作 |
| 规则级 | 中心漂移预测残差>25px仅记录诊断；连续2步编码器不动、连续2次边长变化与指令方向相反 |
| 规则级 | 连续3步前向步深度变化不足2mm（空转步守卫）；对齐步不计入，也不清零 |
| 规则级 | 步数上限、运行时长上限、操作者停止 |

租约到期是**兜底而不是判定**：四条出口（到位、部分响应、断帧、丢目标）都要求先观察到
一件事，`arrival_timeout` 是"这一秒什么都没观察到"时唯一剩下的分支。它的准确含义是
"这条轴没有任何可测反应"，不是"没到位"。

2026-10-18 修正：`arrival_timeout` 恢复本步下发前的 `Goal_Position` 并回读确认，
保留先前承重时的目标误差。日志记录 `previous_goals`、`hold_goals`、`actual_counts` 和
`torque_enabled`。曾尝试用实测位置保持，但操作者报告反复R会下沉，现已撤回该做法；
R 本身不执行扭矩开关。超时仍停止，未自动加大请求或延长租约。

守卫被拒绝时会写清是哪一条，而不是只回一个布尔值。句子按操作者要求**中文为主、英文为辅**
（括号里保留英文关键词，便于 grep），并且同一判定在"下发前"与"执行中"两处出口是同一句：

| 触发的界限 | 实际输出 |
|---|---|
| 标定原始区间 | `目标超出标定原始区间（target outside the calibrated raw range）` |
| 单步上限 | `单步 5.02 度超过上限 5.00 度（wrist_flex：上限 5.00 度 + 到位容差 0.93 度；single joint step exceeds the cap）` |
| 行程预算 | `行程预算已用尽（travel budget 25 mm reached）：相机已移动 28.2 mm` |
| 关节偏移预算 | `关节累计偏移预算已用尽（joint excursion budget 40 deg reached）：已偏 41.8 度` |
| 到位容差内 | `目标全在到位容差内，拒绝发送运动（Refusing motion inside arrival tolerance）` |
| 空转步 | `前向步已无法再接近（forward step no longer closes distance）：连续 3 步深度变化不足 2.0 mm（最后一步 0.0 mm），shoulder_lift 已用 78.2 度偏移；请把标记放近，或确认该轴行程未到限` |

这些句子直接进JSONL的`hold`事件，现场不用再猜。两处出口的差别只在**是否放宽到位容差**：

- **下发前**用严格上限。这里比较的是"意图对意图"，规划器给的步与守卫给的上限必须逐位一致。
- **执行中**用 `上限 + ARRIVAL_TOLERANCE/该轴计数比`。这里比较的是"实测对意图"，而实测本身
  就带±3计数的到位残差；拿严格上限去卡实测，正是守卫拒绝自己合法步的原因——记录姿态下
  1cm前向步需要腕部反转约6.9°，旧5°上限把它截到16计数，也就是上限的99.0%，
  只剩0.049°（0.16计数）余量，任何一次单计数读差都会否掉它。用 `--max-joint-step-deg 12`
  之后，上限本身也不再需要余量。

卡死与深度不一致是"停止并报告"，不是重试：前者说明请求落在死区或机构卡住，
后者说明标记尺寸、焦距或手眼轴向有错，继续动作只会累积错误。

**空转步守卫针对的是"步数烧完但没人知道为什么"。** 440mm 起步时，`shoulder_lift`
到达机械行程端之后，前向原语会进入请求正负交替的状态（`(−24,+38)` 与 `(+26,−38)`
之间来回，达成率 0.12–0.32），闭环一直有步可走、一直不进停靠，最后撞上60步上限
静默结束。守卫的判据是**深度连续3步变化不足2mm**（2mm 低于实测单步前移量的下限，
对齐步既不计入也不清零，否则"接近/对齐"交替永远攒不满3次）。触发时报出的是
**哪条轴已经用掉多少偏移**，因为操作者的下一步取决于这个。

但要说清它在仿真里**没有触发过**：重放全部起点（250–440mm）与全部预算
（120–160°），`dry_steps` 始终为 0。原因是循环其实一直在前进——140° 那一次
`shoulder_lift` 饱和之后，第28→33步仍从 208.9mm 走到 185.7mm（约4.6mm/步），
"边长几乎不动"是拿 trace 的 before 侧比出来的误读。所以它兜住的是另一种失败
（偏移预算把前向能力抽干、只剩无效震荡），而当前真正先触发的是偏移预算停机。
两条消息因此是互补的，不是重复的。

## 7. 计数偏移：每条轴在每个方向先吃掉几个计数

2026-10-18 三轮真机（其中三次以 `arrival_timeout` 停下）暴露出一个比"增益偏弱"更基本的
效应：轴在动之前先吃掉一笔固定的计数。同一姿态、同一段行程下 `wrist_flex` 的实测是

| 请求 | −7 | −7 | −8 | −11 | −14 | −15 | −16 | +5 |
|---|---|---|---|---|---|---|---|---|
| 实测 | 0 | 0 | −2 | −5 | −8 | −9 | −10 | +4 |

负方向 `实测 = max(0, |请求| − 6.5)` 五点全中（差≤1计数），正方向只丢约1个计数。用比例
拟合同一个轴会得到0.57，再拿它预测7计数会得到4——而机构给出0。因此模型改为

`实测 = max(0, |请求| − 偏移) × 增益`，偏移与增益都按关节+方向各存一份。

三个直接后果：

- **规划器要的计数变了。** 想做5个计数的真实运动，请求变成 `5/增益 + 偏移`；腕轴负方向
  从5–7涨到12–14。`expected_counts` 现在描述"扣掉偏移后还剩多少真实位移"，
  `min_effective_counts=5` 的含义也随之改变。
- **最小请求按轴推导。** `minimum_request = 偏移 + OBSERVED_MOTION_COUNTS(2)`，腕轴负方向
  是8.5计数。低于它的一步不发：守卫本来也只能用 `arrival_timeout` 回答。
- **零位移教偏移，不教增益。** 零响应只说明"阈值至少这么大"，所以把偏移按0.5混向请求值；
  斜率只从越过偏移的步里学。旧规则把 −8→−2 记成"只兑现25%"，增益因此掉到0.48，随后
  规划器把请求一路放大到18计数上限。

先验写在 `fixed_rule.MEASURED_COUNT_OFFSETS`，只覆盖被实测过的三条轴
（`shoulder_lift` / `wrist_flex` / `wrist_roll`）。`shoulder_pan` 从未被指令过，它的偏移
保持0、下限保持2计数——这是已知缺口，不是"已经刻画了整条臂"。测试里
`test_an_unmeasured_axis_keeps_a_two_count_floor` 把这个缺口钉住，避免被读成已解决。

## 7.1 跨轴耦合：一条轴"顺带"把标记横向拖走多少

`plan_axis_step` 一次只动一条轴，但它无法只沿图像的一个方向移动标记。姿态变了，图像雅可比
随腕滚转一起转，于是"竖向修正"必然带出一份横向位移。实测（同一标定、同一相机、同一深度）：

| 姿态（wrist_roll） | 竖向轴的横向占比 \|du/dv\| | 来源 |
|---|---|---|
| −92° | 0.16–0.17 | 16:25 运行 |
| −77° | 0.43–0.48 | 17:24 运行 |

原来的规则是 `|cross| ≤ 0.35 × |目标|`，按 0.16 那一档定的。到 −77° 这一档它把所有四条
可用轴同时拒掉（`shoulder_pan` 2.05、`wrist_roll` 6.25 按设计就该拒），17:24 那次运行因此
在**误差 36 px、还剩 80 mm 行程**时停机，报四行一模一样的"no joint reaches the goal
outside deadband"。

两处修正，都是把"拒绝"改成"按实际后果判断"：

- **耦合限值改成看另一轴误差的增长，而不是看这一轴的步长。**
  `grown = |e_⊥ − cross| − |e_⊥|`，只有 `grown > 0.35 × |目标|` 才拒。当另一轴已经对中
  （`e_⊥ = 0`）时它退化成原来的规则；当另一轴也偏着时，"朝目标方向拖"不算漂移。17:24 那一帧
  的残余是 `(25, −26)` px，一条同时把标记横向带回 13 px 的竖步被旧规则当成漂移拒了——而它
  正是横向还欠的那部分。
- **限值本身从 0.35 提到 0.60。** 0.60 是夹出来的，不是挑出来的：它必须高于本臂所有可用轴的
  耦合（0.48），低于"横向运动大于竖向运动"的轴（2.05）。取 0.35 时闭环在第 2 步停机；取 0.60
  时同一帧从 432 mm 连续走到 343 mm，20 步内没有停。

同一次修改里，拒绝信息现在逐轴写明触发的规则和数字（`shoulder_lift 单步 1.5°超过 0.0°`），
并把升档后重复出现的同一组规则合并成一条（`scales 1.35, 1.70: …`）。守卫的拒绝对必须说清
哪条规则生效，这条要求对规划器同样适用。整条信息是中文为主、英文为辅：

```
没有单条关节能实现请求的图像位移（no single joint realizes the requested image shift）：
scale 1.00: shoulder_pan 单步 2.7°超过 0.0°; shoulder_lift 预计位移 4.5 计数 < 死区 5.0; …;
scales 1.35, 1.70: shoulder_lift 单步 2.9°超过 0.0°; …; scale 2.00: shoulder_pan 请求 -19 计数 > 上限 18
```

关节名保持英文标识（它是日志的检索键），规则名与单位用中文；`°` 而不是 `deg`。

回归用例见 `tests/test_fixed_rule_servo.py::DiagonalErrorTest`：它把 17:24 那一帧当成固定
场景，钉住"对角误差时该步被接受且二维误差至少减半"、"另一轴对中时不得选横向占比 2.05 的轴"、
以及"默认限值必须夹在臂自身耦合与横向轴之间"。

| 死区确认 | 同上，观察首个请求 | 记录哪些关节实际不动，不据此改代码 | 逐轴请求与实际 |
| 短接近 | `--rule-max-steps 5 --max-travel-mm 40` | 深度进度单调，无卡死/不一致 | 每步边长、深度进度、增益 |
| 完整接近 | `--rule-max-steps 60`（配置文件里的值） | 到达停靠或预算停止，两者都算正常结束 | 全部JSONL与汇总 |
| 组合 | 先横向偏离再前进 | 对齐相位先修正最大轴，不带着偏置前进 | 相位序列 |

第一次真机试验建议：标记正面、与相机大致垂直、起始距离能看到完整标记且边长约55–65px
（约 **380mm 以内**，名义值，用尺子核对），前方至少350mm无遮挡，手放在Esc上。

起始距离是这次唯一需要现场判断的数：按4.1节的实测，120°偏移预算能覆盖到400mm起步，
但420mm以上就会先耗尽预算，而440mm在任何预算下都到不了停靠。第一次就把标记放在380mm
以内，是为了先确认"能走完"，而不是在预算边缘上判断"为什么停了"。

超过参考起点时启动会提示：400mm只来自固定起始姿态、300mm行程/120°偏移/60步的
参考仿真，不是当前姿态的可达性判定。提示同时列出本次实际预算。命令行
`--rule-max-steps 5 --max-travel-mm 40` 会覆盖profile的60步/300mm，短程试验按预算
停止是正常行为；不会自动提升预算。

```bash
# 只读：确认检测、边长与名义深度
eai-course vision --fixed-rule --camera-index 0 --preview

# 真机：显式执行（预算取自配置文件）
eai-course vision --profile configs/visual_servo/aruco_fixed_rule.toml \
  --camera-index 0 --execute --preview --rule-max-steps 5 --max-travel-mm 40

# 走完整个接近：不再覆盖预算，用配置文件里的 60 步 / 300mm / 120°
eai-course vision --profile configs/visual_servo/aruco_fixed_rule.toml \
  --camera-index 0 --execute --preview
```

命令行上限现在是 `--max-joint-excursion-deg ≤ 120`、`--max-travel-mm ≤ 320`、
`--rule-max-request-counts ≤ 60`。这些是**允许的上限**，不是推荐值；放宽超过配置文件
还需要现场重新确认前方净空，并把这个确认写进当天的记录，而不是改默认值。

`--camera-fps` 的默认值来自 `configs/hardware.local.toml` 的 `[camera].fps`（示例配置写 30）。
lerobot 会回读相机实际帧率，误差超过 0.1% 就报 `failed to set fps=15 (actual_fps=30.0)`——
这不是故障，是驱动不支持该帧率且不肯静默降级。本机的 C1（UVC）在 640×480 只给 30，
所以配置里写 30；换机器时先确认该机相机报的帧率。索引与帧率可用下面这段确认：

```bash
.venv/bin/python -c "
import cv2
for i in range(4):
    c = cv2.VideoCapture(i)
    if not c.isOpened(): print(i, 'not opened'); continue
    c.set(cv2.CAP_PROP_FRAME_WIDTH, 640); c.set(cv2.CAP_PROP_FRAME_HEIGHT, 480)
    ok, _ = c.read()
    print(i, 'opened', ok, int(c.get(cv2.CAP_PROP_FRAME_WIDTH)),
          int(c.get(cv2.CAP_PROP_FRAME_HEIGHT)), round(c.get(cv2.CAP_PROP_FPS), 2))
    c.release()
"
```

机器上同时挂着内置相机或 iPhone 连续互通相机时，索引会随拔插改变。腕部相机认错了的表现是
预览里看到房间而不是标记，状态停在 `TARGET WAIT - HOLD`，一条 `observation` 都不会写。

日志写入 `local_artifacts/experiments/<时间戳>_fixed-rule.jsonl`，事件顺序为
`settings → observation → plan → feedback → ... → reached|hold → summary`。

## 9. 明确未宣称的内容

- 已有真机短程执行日志，但完整停靠尚未验收；起点范围表仍为仿真。
- 空转步守卫与起点可达范围提示**只在仿真里验证过**：全部起点与预算重放下 `dry_steps`
  始终为0，警告文案的"约209mm"取自440mm那一行。真机上它是否触发、触发了报的轴名对不对，
  要等第一次执行才能确认。
- 前向步在**真机**上会带出约 20 px 的中心漂移（17:24 之后闭环每一步 `approach` 都把 |e| 推回
  20–30 px，随后靠 `align` 拉回），而同一个修复在离线重放里只有 5.2–5.8 px。这个 17–20 px 的
  差额与"图像/模型在深度方向上差 13 倍"是同一个未解问题；跨轴限值不修它，只是不再因为修不了
  的竖向误差而停机。
- 预算（300mm / 120° / 12° / 40计数 / 60步）是操作者现场确认的**许可**，不是测量出来的无碰撞
  工作空间；4.1节的表格是同一个模型下的重放，不是真机测量。
- 440mm 起步到不了 120px 停靠。原因是**前向原语把 `shoulder_lift` 一路推到它自己的机械行程端**
  （+97.35° / 上限 +100°），**不是**"前向几何极限"：这条轴单独运动时相机最近只到 330.6mm（+13°），
  再往上就翻过标记；而终点姿态上它每多一度仍能靠近 2.64mm。所以"到不了"是行程耗尽，
  不是几何不可能。让 `elbow_flex` 分担前向位移曾被实现并实测，**结果是更差**（4.2节）：
  腕轴要替它多付 counter-rotation，单步最大负载反而上升。该限制仍然成立。
- "1cm"是规则给出的相机平移意图，不是已测的物理位移；每步实际位移由关节解与
  实测响应决定，报告里给的是 `achieved_fraction` 与预测平移。
- 名义深度依赖一份未独立复核的内参，不作为距离测量使用。
- 没有碰撞或测距传感器；行程预算是模型预算，不是已外部测量的无碰撞工作空间。
- 不宣称比第一轮的39.4px中心精度更好；本轮优化的是前向能力，中心精度待真机重测。
- 失败索引、原始日志、标定快照按第一轮的做法归档后再谈"可复现"。

## 10. 与"任意物体"扩展的兼容性

任意物体那一轮（见 `visual_servo_any_object.md`）没有删除本文的任何代码路径：
`camera_step.py` 626 行、`fixed_rule_servo.py` 389 行、`aruco_fixed_rule.toml` 24 行
均未改动。`fixed_rule.py` 从 389 行增至 474 行，增加的全部是可选字段与两阶段挂载：

| 新增 | 缺省时的行为 |
|---|---|
| `Observation.extent_px = None` | `side_px` 回退到 `marker_side_px(corners)`，即第一轮口径 |
| `Observation.extent_name = "side"` | ArUco 的约定，与 pinhole 路线一致 |
| `Observation.from_geometry()` | 新入口，不被旧路径调用 |
| `controller.scale = None` | `depth_m` 仍走 `focal_px` + `marker_length_m` |
| `controller.use_scale()` | 不调用则永不挂载 |
| `controller.depth_of()` | `record` 专用的无校验版本 |

唯一的行为放宽是四角点允许贴边（`>=` 改为 `>`）：内缩在画面里的 ArUco 目标不受影响。

这些是断言，不是承诺——`tests/test_fixed_rule_servo.py::BaseVersionCompatibilityTest`
逐条固定：三元点构造的 `side_px` 必须等于 `marker_side_px`；`scale=None` 时
`depth_m` 与 `depth_of` 必须与 `depth_from_side_px` 逐位相等（12 位小数）；
`decide()` 在该输入下必须给出 `move`；同一目标经几何层绕一圈回来，请求的关节计数
必须完全相同。任一条被改坏，先红的是测试，不是录 demo 的那一刻。
