# 任意物体伺服：从 ArUco 扩展到"任何东西"

状态：**骨架已落地、离线验证通过；尚未在真机执行**。
本文所有数值都可复算：要么来自真实标定文件与真实 URDF，要么是常数算术，
没有一项是"跑出来感觉不错"。真机分级验收见第 8 节。
需要操作者拍板的项集中在[决策清单](object_servo_decisions.md)。

## 1. 规则没有变

五区域、1cm 一步、到达停靠就保持。变的只是"目标从哪来"：

| 项 | ArUco 路径 | 任意物体路径 |
|---|---|---|
| 目标表示 | 四个角点 + 边长 | `TargetGeometry`（中心/表观尺寸/支撑点） |
| 表观尺寸的度量尺寸 | 印刷边长 25mm | 一次参考测量，或用真实尺寸 |
| 谁来提供每帧位姿 | 每帧重新解码 | 光流每帧 + 检测器仲裁 |
| 决策与执行 | 不变 | **不变** |

所以 `control/visual_servo/fixed_rule.py` 与 `camera_step.py` 一行没改逻辑，
只是把输入的类型从"四角点"放宽成"任意几何 + 任意尺度"。

## 2. 必须被替换的三件事

**（a）四角点是标记专属的。** 圆没有角，手没有正方形，掩膜两样都没有。但规则真正
只问三个问题——在哪、看起来多大、相机该往哪动——所以表示可以一般化。
`vision/geometry/targets.py` 的 `TargetGeometry` 就回答这三个：

| 字段 | 含义 | 谁在用 |
|---|---|---|
| `center_px` | 目标在哪 | 五区域分类、居中误差 |
| `extent_px` | 一个随距离缩小的标量长度 | 停靠判据、深度、前向步的深度列 |
| `support_px` | 交互矩阵在这些点上求值 | `camera_delta_goal`、`plan_camera_step` |

`extent_px` 是**约定**，不是测量值，所以约定必须随几何一起走：

| `extent_name` | 定义 | 与之配对的度量量 |
|---|---|---|
| `side` | 闭合多边形平均边长 | 正方形边长 |
| `diameter` | 直径 | 圆的真实直径 |
| `sqrt_area` | 像素面积开方 | 轮廓真实面积开方 |
| `span` | 最长弦 | **没有形状无关的配对量** |

配错就是系统性错误：正方形边长配对角线的真实长度，深度差 1.41 倍。因此
`ExtentScale` 把约定写进自身，决策层在约定不一致时直接 hold，而不是算出一个
"看起来很合理"的深度。

**（b）"焦距 × 标记边长"不是唯一的路。** 针孔关系里
`focal_px · extent_m` 对一个给定目标是**一个常数**，而这个常数也能从一次距离测量得到：

```
k = focal_px · extent_m          # 标定路线：内参 + 真实尺寸
k = depth_ref_m · extent_px_ref  # 参考路线：卷尺 + 那一次的像素读数
```

两条路完全等价，`ExtentScale` 用同一个类型表达。重要之处在于：**没人能说出一个咖啡杯
有多少米"表观尺寸"**，因为那个量是跟踪器点集的性质、不是杯子的性质；但任何人都能把杯子
放在量过的距离上读一次像素。

算例（可复算）：参考距离 300mm 时读到 60px ⇒ `k = 0.3 × 60 = 18 m·px`。
于是 `depth = 18 / 60 = 0.30m`（自洽），`depth = 18 / 66 = 0.273m`。
注意深度误差等于 `k` 的相对误差：卷尺差 10mm，300mm 处就是 3.3% ⇒ ±10mm。
所以**停靠判据仍然用像素**，深度只用于报告与门限。

**（c）单帧检测不能驱动回路。** 见下一节。

## 3. 跟踪器只允许报三种状态

`vision/tracking/base.py` 把"追踪器"定义成契约而不是实现，因为实现差异极大：
一次 fiducial 解码是精确的、1 毫秒；手部关键点网络是几十毫秒；分割模型可能是四分之一秒。

| 状态 | 承诺 | 运动回路可否据此发步 |
|---|---|---|
| `tracking` | 这一帧本身测到了 | 可以（`is_fresh`） |
| `coasting` | 这一帧没测到，但有近期验证过的状态在沿用 | 可以，但受时长上界约束 |
| `lost` | 什么都没有 | **不可以**，必须保持 |

关键点是 `coasting` 的**上界属于契约本身**，不是各实现自己发明的一个可调项。
一个能无限 coast 的跟踪器，会朝着漂移指的方向把机械臂推过去。

## 4. 为什么必须融合

相机 15fps ⇒ 每帧 **66.7ms**。目录里声明的延迟量级换算成帧：

| 检测器 | 延迟量级 | 落后帧数 |
|---|---|---|
| `mediapipe-hands` | 30ms | 0.45 |
| `yolo-world` | 80ms | 1.2 |
| `sam2` | 250ms | 3.75 |
| `owlv2` | 350ms | 5.25 |

一个 1cm 步在 300mm 处只让表观尺寸变化 `10/290 = 3.45%`：60px 的目标只有
**2.07px**，第一轮实测的 70.4px 边长也只有 **2.43px**。而 350ms 的检测器给出的位姿，
在你拿到它的时候已经过时五帧；直接用它的尺寸差分当深度信号，等于在噪声上再叠一层滞后。

所以分工是：

| 谁 | 负责 | 频率 |
|---|---|---|
| 光流（`SupportPointTracker`） | 每帧位姿 | 每帧 |
| 检测器 | 它是什么、丢了以后重新找到 | 有界、异步、可慢 |
| `FusedTracker` | 仲裁：一致就继续，冲突就重锚，死了就重捕获 | 每帧 |

**这不是滤波器，是监督器。** 没有任何地方把一个慢测量平均进一个快测量：
新鲜位姿与陈旧位姿的平均，就是一个误差棒更小的陈旧位姿。

## 5. `SupportPointTracker`：一个相似变换，不是逐点运动

四个支撑点由区域内的纹理 k-means 得到，每帧只估计**一个 4 自由度相似变换**
（平移+旋转+等比缩放），因此"点动了"和"看起来变大了"永远不可能互相矛盾。

反面做法是每帧重拟合包围盒：一个 1cm 步在 300mm 处让 70px 物体的边长变 2.4px，
而包围盒的逐帧抖动就有 2–3px——信号被噪声吃掉。

它还拒绝不可能的尺度跳变（单帧 `max_scale_step=1.25`）与前后向光流不一致的点。
它只报 `tracking` / `lost`：它没有"正在思考"的模型可以等，coasting 只属于知道
有模型在算的那一层。

代价也必须说清：**它不知道自己在跟什么**。目标转出纹理、滑到背景上、被遮挡，
它都会跟丢，而且丢了以后自己回不来。

## 6. `FusedTracker` 的状态机

| 本帧情况 | 输出 | 说明 |
|---|---|---|
| 光流可用 | `tracking`，用光流几何 | 常规情况 |
| 光流可用 + 新检测且两者一致 | `tracking`，用光流几何 | 一致**不重锚**，不去打扰一个好的跟踪器 |
| 光流可用 + 新检测但冲突 | 重锚到检测，`tracking` | 语义赢：光流只知道"像素动了" |
| 光流死 + 新检测 | 重捕获到检测框，`tracking` | `reacquisitions` 加一 |
| 光流死 + 检测太旧 | `lost` | 必须保持 |

一致性判据：

- 中心距离 ≤ `0.35 × max(两个 extent)`。用相对量而不是像素，因为同样的物理误差
  在近处是 20px、远处是 3px。60px 目标下即 21px 窗口。
- 表观尺寸比在 `1 ± 0.35` 内，且**先把两边换算到等面积正方形边长**再比。
  `sqrt(π)/2 = 0.886`——直径与等面积边长差 13%，与一步的尺寸变化同量级。
  `span` 无法换算，就跳过尺寸检查**并且记一笔** `convention_skips`；
  假装它们相等，会让旋转的物体看起来像在靠近。

另外两条实现约束：

- **一帧只推进一步。** 运动守卫会在下发目标前读一帧并检查目标仍在，那是同一帧被第二个
  调用方消费。同一帧推进两次光流要么重复计数运动，要么被判成帧间隔而报丢——所以按
  数组身份去重。
- **检测器胜出时不假装这是测量。** 检测结果来自更早的帧，报 `coasting` 而不是
  `tracking`；`is_fresh` 为假，调用方一眼能分辨。

第三种模式 `--tracker detector` 不是"降级"，是真实选择：手是形变体，光流在手指张合时
必然漂，此时几十毫秒的关键点模型本来就是更好的跟踪器。它每一帧都是 coasting
（检测必然来自更早的帧），由上界兜住。

## 7. 运行器与守卫

`applications/visual_servo/object_servo.py`。守卫完全复用：

| 守卫 | 内容 |
|---|---|
| `BoundedJointMotion` | 标定范围、工作空间、关节/行程/单步预算、下发前的新鲜目标检查、扭矩与状态回读、到位租约 |
| 目标新鲜度 | `stale(geometry, now, max_age_s)`，默认 0.25s；过期即 hold，不下发 |
| 拒绝原因 | 守卫返回句子而不是布尔：`planned step not permitted: <reason>` |
| 归因锚点 | `bounds.last_before`，守卫写目标前那一刻的编码器读数 |

`TrackerDetectionAdapter` 把跟踪器包成守卫认识的 `detect(frame) -> (标注, 掩膜)` 形状，
因此守卫一行没改。这也是为什么"目标在运动中丢失"这条既有保护自动适用于任意物体：
适配器返回 `None`，守卫就按原有的丢失处理写保持目标。

## 9. 离线闭环证据（仿真，不是真机）

`tests/test_object_servo.py` 跑的是**真决策 + 真守卫 + 真日志 + 假电机**：
目标几何由真实 URDF、真实手眼矩阵、真实内参把记录姿态投影出来，
执行模型带上第一轮实测的三个缺陷（5计数死区、2计数到位残差、负向偏弱的手腕）。

一次跑到行程预算为止的结果（`--reference-depth-m 0.30`，参考即真实 300mm）：

| 指标 | 结果 |
|---|---|
| 步数 | 9 步，全部 `verdict ok`（无 `stall`、无 `center_drift`、无 `depth_disagreement`） |
| 表观尺寸 | 70.4 → 85.1 px（`side`） |
| 报告深度 | 300 → 248 mm |
| 行程 | 60.4 mm（随后被守卫以"travel budget 60 mm reached"拒绝，不是规则自己停的） |
| 前向步实际计数 | `shoulder_lift +14` 配 `wrist_flex −13 / −14`，与第一轮实测的配对一致 |
| 质心误差 | 先 39px → 27px → 16px 进 approach 门限，之后稳定在 7–10px |

有一条必须点名：第 5 条 feedback 只落实了 **3.4mm** 行程、实际计数 `shoulder_lift +4`。
模型按实测记录了这次部分响应，没有把它当作完整一步。这说明死区/整步缩放的路径
在闭环里真的会生效——不是只在单元测试里生效。

这些数字**不是**精度声明：它们是"管路连通、守卫生效、归因正确"的证据。
精度要等 L3/L4 真机。

## 10. 本设计不宣称的东西

- 不宣称任何精度的提升。真机一步没跑过。
- 不宣称深度可信到毫米。深度相对误差 = 那一次参考测量的相对误差。
- 不宣称追动目标的能力。规则假设目标静止（采样取多帧中位数）；手在被追的时候
  也在动，这是[决策清单 H 项](object_servo_decisions.md)尚未回答的问题。
- 不宣称 `dark-blob` 是"任意物体"。它的作用是**先把管路跑通**：异步、几何转换、
  融合、固定规律整条链路都被它验证过，之后任何回归都能归因到换上的模型，
  而不是归因到管路本身。
- 不宣称已经实现任何大模型检测器。目录里四条只有声明与缺依赖报文，没有实现。
